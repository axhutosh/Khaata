# Khaata — developer setup

How to run, test and configure Khaata locally. The product overview is in the top-level
`README.md`; scope and decisions are in `docs/PRD.md`, the design system in `docs/DESIGN.md`,
and orientation for an AI coding session in `CLAUDE.md`.

```
khaata-app/
├── backend/            FastAPI app
│   ├── app/
│   │   ├── main.py         app, middleware, routers, startup migrations
│   │   ├── config.py       settings (from backend/.env)
│   │   ├── models.py       User, Upload, Transaction, MerchantRule, Budget
│   │   ├── auth.py         sessions            passwords.py  scrypt hashing + rules
│   │   ├── security.py     headers, CSRF origin check, throttling
│   │   ├── crypto.py       narration encryption at rest (DATA_KEY)
│   │   ├── extractor.py    decrypt → parse → categorise → balance check (SBI; PDF + Excel)
│   │   ├── names.py        person-vs-business signals for P2P detection
│   │   ├── insights.py     dashboard numbers      recurring.py  subscriptions & regular payments
│   │   └── routers/        auth, upload, uploads, transactions, insights, budgets
│   ├── samples/        synthetic SBI statements (samples/real/ is git-ignored)
│   ├── tools/          mask_statement.py, set_password.py
│   └── tests/
├── frontend/           Vite + React (src/pages, src/components, public/ icons)
└── branding/           logo files (generated by frontend/scripts/make_brand.py)
```

## Run it

**Backend** (Python 3.11+)

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
cp .env.example .env            # then set SECRET_KEY and DATA_KEY (commands are in the file)
uvicorn app.main:app --port 8000          # http://localhost:8000  (API docs at /docs)
```

`--reload --reload-dir app` also works, but on some Windows setups the reloader misses edits —
restart after backend changes. The server refuses to start without a valid `DATA_KEY`.

**Frontend** (Node 18+)

```bash
cd frontend
npm install
npm run dev                     # http://localhost:5173
```

The Vite dev server proxies `/api/*` to the backend, so the session cookie is same-origin.

**Tests**

```bash
cd backend
python -m pytest
```

Throwaway SQLite DB and the sample PDFs. No Alembic yet: schema fixes live in
`main.migrate_data`; for anything bigger, delete `backend/khaata.db` and restart.

```bash
cd backend

```

## Settings (`backend/.env`)

| Setting | What it does |
| --- | --- |
| `SECRET_KEY` | Signs session cookies and upload-preview tokens. 32+ random characters. |
| `DATA_KEY` | Encrypts stored bank narrations. **Back it up** — lose it and they're unreadable. Rotate with `DATA_KEY=new,old`, restart, then drop the old key. |
| `OPEN_SIGNUP` | `true` (default): anyone can create an account. `false`: only `ALLOWED_EMAILS`. |
| `ALLOWED_EMAILS` | Comma-separated emails that may sign up when `OPEN_SIGNUP=false`. |
| `ENV` | `production` refuses unsafe defaults, turns on HTTPS-only cookies and hides `/docs`. |
| `CORS_ORIGINS` | The frontend origin(s); writes from anywhere else are refused. |
| `SESSION_MAX_AGE`, `SESSION_SECURE`, `MAX_UPLOAD_MB` | Sign-in lifetime, HTTPS-only cookie, upload cap. |

## Security

- **Accounts**: email + password, hashed with scrypt. Passwords need 10+ characters, can't be a
  common password or contain the email name. Sign-up is open by default; each account is
  sealed off from the others (`tests/test_isolation.py`).
- **Every API needs a session** except `/auth/signup`, `/auth/login`, `/auth/logout`,
  `/auth/config` and `/health` — enforced per router in `app/main.py` and checked by a test
  that walks every route.
- **Session**: signed, HttpOnly, SameSite=Lax cookie, 7 days by default, HTTPS-only in
  production; signing in starts a fresh session.
- **Cross-site requests**: writes from an origin outside `CORS_ORIGINS` are refused (CSRF).
- **Throttling**: 5 failed sign-ins per email (20 per address) in 15 minutes; 10 new accounts
  per address per hour. A wrong email and a wrong password get the same answer.
- **Statements**: the PDF password is used once and never stored; uploads are capped.
- **Encryption at rest**: narrations are Fernet tokens under `DATA_KEY`; the duplicate-check
  hash is a keyed HMAC. Amounts, dates, merchants and categories stay readable for insights.
- **Responses**: `no-store`, `nosniff`, `DENY` framing, locked-down CSP.

## Sharing a real statement safely

To tune the extractor to a real SBI layout without sharing personal data:

```bash
cd backend
# put the PDF or Excel file in backend/samples/real/  (git-ignored)
.venv/Scripts/python tools/mask_statement.py samples/real/statement.pdf
```

It asks for the PDF password (not shown, not stored) and writes `statement.masked.txt` /
`.masked.json` next to it: names, account and reference numbers, UPI IDs, IFSC and address
become `XXXX` / `9999`; dates, amounts, balances, SBI layout words and well-known business
names stay. **Read the .txt before sharing.** `--keep WORD,WORD` leaves more business names visible.
